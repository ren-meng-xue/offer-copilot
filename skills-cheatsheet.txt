Offer Copilot 技能速查表
生成时间：2026-05-06

说明
- 这个文件整理了当前仓库里可见的 gstack 和 superpowers 技能。
- 按实际使用场景分类：开发、设计、运维/发布、营销/产品、规划/架构、复盘/知识沉淀、工作流。
- 每个技能都说明三件事：它是干什么的、什么时候用、怎么调用。

怎么用技能
- 直接调用：明确输入技能名，例如 `/investigate`、`/ship`。
- 自然语言触发：直接描述你的需求，有些技能会根据语义自动建议或触发。
- 实际建议：不要依赖自动触发。只要你已经知道自己要用哪个，就直接手动调用。

常见调用方式
- 显式调用：
  - `/office-hours`
  - `/plan-eng-review`
  - `/investigate`
  - `/review`
  - `/qa`
  - `/ship`
- 自然语言示例：
  - “帮我脑暴一下这个想法” -> `office-hours`
  - “帮我看下架构” -> `plan-eng-review`
  - “帮我查这个 bug” -> `investigate`
  - “帮我 review 一下这次改动” -> `review`
  - “帮我测一下这个功能” -> `qa`
  - “帮我提 PR” -> `ship`

==================================================
一、最常用的一批
==================================================

这些是你平时最值得记住的：
- `/office-hours`
- `/plan-eng-review`
- `/investigate`
- `/review`
- `/qa`
- `/ship`

可以这样记：
- 写代码前：`/office-hours`、`/plan-eng-review`
- 遇到问题：`/investigate`
- 写完以后：`/review`、`/qa`
- 准备提交：`/ship`

==================================================
二、按类别整理
==================================================

【开发类】

investigate（gstack）
- 作用：排查 bug、异常、报错、不符合预期的行为。
- 什么时候用：你已经遇到问题，但还没找到根因。
- 怎么用：输入 `/investigate`，或者直接说“帮我查这个 bug”“帮我定位这个报错”。

review（gstack）
- 作用：做代码审查，重点看 bug、回归风险、测试缺口、设计问题。
- 什么时候用：功能写完后，准备合并前，或者你想让系统帮你挑问题。
- 怎么用：输入 `/review`，或者说“帮我 review 这次改动”。

qa（gstack）
- 作用：做功能验证和端到端检查，看功能实际上能不能跑通。
- 什么时候用：你想验证页面、接口、交互流程是否真实可用。
- 怎么用：输入 `/qa`，或者说“帮我测一下这个流程”“这个能跑通吗”。

qa-only（gstack）
- 作用：只做 QA，不扩展到更大范围的方案或代码分析。
- 什么时候用：你只想验证功能本身，不想带出额外评审。
- 怎么用：输入 `/qa-only`。

careful（gstack）
- 作用：用更保守、更谨慎的方式处理任务。
- 什么时候用：改动涉及认证、支付、数据库、共享基础设施、影响面大时。
- 怎么用：输入 `/careful`。

guard（gstack）
- 作用：在高风险操作前做保护性检查。
- 什么时候用：上线前、做关键改动前、怕误伤时。
- 怎么用：输入 `/guard`。

pair-agent（gstack）
- 作用：用“结对协作”的方式处理复杂任务。
- 什么时候用：一个任务你想多一层结构化思考，或者需要更稳一点的推进。
- 怎么用：输入 `/pair-agent`。

codex（gstack）
- 作用：显式走 gstack 的 codex 工作流。
- 什么时候用：你明确想进入这套 workflow。
- 怎么用：输入 `/codex`。

systematic-debugging（superpowers）
- 作用：系统化调试，不是乱试，而是一步步缩小范围。
- 什么时候用：问题复杂、现象混乱、容易误判时。
- 怎么用：按名字调用，或者明确说要“系统化排查”。

test-driven-development（superpowers）
- 作用：按 TDD 方式开发，先测试后实现。
- 什么时候用：你想更稳地推进实现，尤其是业务逻辑变化较大时。
- 怎么用：按名字调用。

verification-before-completion（superpowers）
- 作用：在宣布“做完了”之前做最后核验。
- 什么时候用：收尾阶段，避免“以为做完其实没验”。
- 怎么用：按名字调用。

finishing-a-development-branch（superpowers）
- 作用：功能完成后，决定是合并、开 PR、保留分支还是丢弃。
- 什么时候用：测试通过，开发已完成，准备处理分支。
- 怎么用：按名字调用。

subagent-driven-development（superpowers）
- 作用：用多 agent 拆解复杂开发任务。
- 什么时候用：需求较大、步骤多、适合拆分并行推进时。
- 怎么用：按名字调用。

dispatching-parallel-agents（superpowers）
- 作用：把互不冲突的任务并行分发出去。
- 什么时候用：多个子任务之间互相独立时。
- 怎么用：按名字调用。

using-git-worktrees（superpowers）
- 作用：用 git worktree 隔离开发工作区。
- 什么时候用：你不想污染当前工作区，或者要并行处理多个任务时。
- 怎么用：按名字调用。

【规划 / 架构类】

office-hours（gstack）
- 作用：前期脑暴，帮你想清楚值不值得做、从哪里切入、范围怎么收。
- 什么时候用：有新想法、产品方向不清楚、想判断是否值得做时。
- 怎么用：输入 `/office-hours`，或者说“帮我想想这个 idea”“这个值不值得做”。

plan-eng-review（gstack）
- 作用：从工程角度审实施方案，重点看架构、数据流、边界情况、测试、性能。
- 什么时候用：准备开工前，方案已有雏形，但想先做技术评审时。
- 怎么用：输入 `/plan-eng-review`，或者说“帮我看下架构”“帮我审一下技术方案”。

plan-ceo-review（gstack）
- 作用：从产品/策略/范围的角度审方案。
- 什么时候用：你想先确认需求定位、价值、切入点，而不是马上看代码设计。
- 怎么用：输入 `/plan-ceo-review`。

autoplan（gstack）
- 作用：自动串起更完整的计划流程。
- 什么时候用：你想让系统帮你跑一套更完整的规划和评审过程。
- 怎么用：输入 `/autoplan`。

plan-tune（gstack）
- 作用：优化已有计划。
- 什么时候用：方案已经有了，但你觉得还不够稳、范围不够准、顺序不够清楚。
- 怎么用：输入 `/plan-tune`。

plan-design-review（gstack）
- 作用：审设计方案，而不是审代码实现。
- 什么时候用：UI/交互方案已经有了，想先评审再开发。
- 怎么用：输入 `/plan-design-review`。

plan-devex-review（gstack）
- 作用：审“开发体验改造计划”。
- 什么时候用：你要改脚手架、文档、开发流程、本地启动、调试体验之类的东西。
- 怎么用：输入 `/plan-devex-review`。

writing-plans（superpowers）
- 作用：产出实施计划。
- 什么时候用：还没开工，想先写出明确执行步骤时。
- 怎么用：按名字调用。

executing-plans（superpowers）
- 作用：按计划执行，而不是边做边乱改。
- 什么时候用：计划已经成型，准备进入严格执行阶段时。
- 怎么用：按名字调用。

【设计类】

design-consultation（gstack）
- 作用：讨论 UI/UX 方向，偏前期咨询。
- 什么时候用：界面或交互还没定型，需要先聊方案时。
- 怎么用：输入 `/design-consultation`。

design-review（gstack）
- 作用：审界面质量、交互细节、视觉完成度。
- 什么时候用：前端做完之后，想看看好不好用、顺不顺、是否有粗糙感。
- 怎么用：输入 `/design-review`。

design-html（gstack）
- 作用：更偏向把设计思路直接落到 HTML 产物。
- 什么时候用：你想快速得到偏 HTML 实现的设计产出。
- 怎么用：输入 `/design-html`。

design-shotgun（gstack）
- 作用：一次给出多个设计方向，而不是只给一个方案。
- 什么时候用：你还在探索阶段，不想太早锁死。
- 怎么用：输入 `/design-shotgun`。

spec-flowchart（superpowers）
- 作用：把规格说明或流程变成流程图式结构。
- 什么时候用：复杂逻辑、审批流、状态流、业务流需要更直观表达时。
- 怎么用：按名字调用。

【运维 / 发布类】

ship（gstack）
- 作用：进入交付流程，通常会涉及测试、整理 diff、push、创建 PR。
- 什么时候用：一个功能已经准备提交上游，或者你想发起合并流程。
- 怎么用：输入 `/ship`，或者说“帮我提 PR”“帮我发出去”。

land-and-deploy（gstack）
- 作用：比 `ship` 更进一步，偏向“落地并部署”。
- 什么时候用：不仅要提交代码，还要推进合并和部署时。
- 怎么用：输入 `/land-and-deploy`。

setup-deploy（gstack）
- 作用：准备部署流程和部署配置。
- 什么时候用：需要把项目接入部署流程、改部署方式、补环境时。
- 怎么用：输入 `/setup-deploy`。

canary（gstack）
- 作用：做金丝雀/小流量发布思路。
- 什么时候用：你不想一次性全量上线，希望更稳地灰度验证。
- 怎么用：输入 `/canary`。

health（gstack）
- 作用：检查系统健康状态。
- 什么时候用：服务不稳、上线后想快速看整体状态、怀疑环境异常时。
- 怎么用：输入 `/health`。

freeze（gstack）
- 作用：进入冻结状态，暂停高风险变更。
- 什么时候用：上线窗口、关键阶段、需要控变时。
- 怎么用：输入 `/freeze`。

unfreeze（gstack）
- 作用：解除冻结。
- 什么时候用：冻结窗口结束后恢复正常开发节奏。
- 怎么用：输入 `/unfreeze`。

document-release（gstack）
- 作用：整理发布文档或发布说明。
- 什么时候用：发版本、写 release notes、做交付说明时。
- 怎么用：输入 `/document-release`。

【营销 / 产品探索类】

office-hours（gstack）
- 作用：产品方向脑暴。这个技能既属于规划，也适合产品探索。
- 什么时候用：判断想法值不值得做、卖点是否清楚、从哪里切进去更合适。
- 怎么用：输入 `/office-hours`。

plan-ceo-review（gstack）
- 作用：从产品与策略角度收紧范围。
- 什么时候用：你想先看定位和价值，而不是直接看技术方案。
- 怎么用：输入 `/plan-ceo-review`。

landing-report（gstack）
- 作用：对落地页做分析或生成相关报告。
- 什么时候用：你要看落地页表现、结构、表达、问题点时。
- 怎么用：输入 `/landing-report`。

browse（gstack）
- 作用：浏览网站内容、看外部页面。
- 什么时候用：需要查资料、看线上页面、看竞品信息时。
- 怎么用：输入 `/browse`。

scrape（gstack）
- 作用：抓取网页内容用于分析。
- 什么时候用：你要把某个页面的内容提取下来再处理时。
- 怎么用：输入 `/scrape`。

【上下文 / 知识沉淀类】

context-save（gstack）
- 作用：保存当前进度、思路、决定、下一步。
- 什么时候用：长任务中途暂停、要切任务、怕上下文丢失时。
- 怎么用：输入 `/context-save`。

context-restore（gstack）
- 作用：恢复之前保存的上下文。
- 什么时候用：重新开始接着干某个任务时。
- 怎么用：输入 `/context-restore`。

learn（gstack）
- 作用：沉淀这次任务中学到的东西。
- 什么时候用：你发现了坑、规律、经验，想让后续任务复用时。
- 怎么用：输入 `/learn`。

setup-gbrain（gstack）
- 作用：配置 gbrain/gstack 的记忆能力。
- 什么时候用：第一次搭建长期记忆能力时。
- 怎么用：输入 `/setup-gbrain`。

sync-gbrain（gstack）
- 作用：同步 gbrain 状态。
- 什么时候用：你希望记忆层和当前工作保持同步时。
- 怎么用：输入 `/sync-gbrain`。

make-pdf（gstack）
- 作用：生成 PDF。
- 什么时候用：需要把内容导出成 PDF 交付时。
- 怎么用：输入 `/make-pdf`。

【复盘 / 质量提升类】

retro（gstack）
- 作用：做复盘，总结哪里做得好，哪里踩坑。
- 什么时候用：一个功能、一个阶段、一次交付结束后。

- 什么时候用：本地启动慢、日志差、文档乱、开发命令不好用时。

cso（gstack）
- 作用：偏高层视角的审视或策略判断。
- 什么时候用：你希望有一个更偏管理/策略层的视角来审这个事情。

skillify（gstack）

- 什么时候用：你发现一类工作反复出现，想标准化处理时。

==================================================
四、自动触发还是手动触发
==================================================

结论很简单：
- 有些技能支持自动建议或自动触发
- 但不要依赖这个能力
- 最稳的方式还是你自己手动叫

建议你这样理解：
- 自动触发：只是辅助
- 手动调用：才是主路径

什么时候适合手动叫
- 你已经知道自己要干什么
- 你不想赌系统能不能猜对
- 这个任务比较重要，不能走偏

什么时候可以等它建议
- 你只是随口描述一个需求
- 你自己也不确定该用哪个技能

五、最简单的记忆方式
==================================================

先只记 6 个：
- `/office-hours`
- `/plan-eng-review`
- `/investigate`
- `/review`
- `/qa`
- `/ship`

它们几乎覆盖你平时最常见的开发流程：
- 想法阶段 -> `/office-hours`
- 技术方案阶段 -> `/plan-eng-review`
- 遇到 bug -> `/investigate`
- 写完看风险 -> `/review`
- 验证功能 -> `/qa`
- 准备提交 / PR -> `/ship`
