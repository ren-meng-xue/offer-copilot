PostgreSQL / pgvector / ORM / Alembic 速记

1. 三层关系

- ORM 模型：Python 层定义表结构。
- Alembic 迁移：把表结构和索引真正执行到数据库里。
- PostgreSQL 表：数据库里最终落地的真实表和索引。

一句话：
ORM 负责“定义”，Alembic 负责“执行”，数据库里才会真正“存在”。


2. 这个项目里的 ORM 模型

- KnowledgeBase 对应数据库表 knowledge_bases
- DocumentChunk 对应数据库表 document_chunks

DocumentChunk 里最关键的字段是：

- embedding: Vector(1536)

意思是：
- document_chunks 表里有一个 embedding 列
- 类型是 1536 维向量
- 对应 OpenAI text-embedding-3-small 的输出维度


3. 为什么不能只写 ORM

ORM 只是 Python 代码里的表定义。
如果只改 ORM，不做迁移：

- Python 代码知道有这个字段
- 但数据库里可能根本没有这张表或这个字段

所以正确流程是：

1) 写或修改 ORM 模型
2) 写或生成 Alembic 迁移
3) 执行 alembic upgrade head
4) 数据库结构真正更新


4. Alembic 里的 op 是什么

op 是 Alembic 的操作入口。

常见用法：

- op.create_table(...)    建表
- op.drop_table(...)      删表
- op.execute(...)         执行原生 SQL

注意：
op 不是表字段，也不是模型属性。
它只是迁移脚本里操作数据库的工具对象。


5. pgvector 是什么

pgvector 是 PostgreSQL 的 extension（扩展）。

作用：

- 支持 vector 向量列类型
- 支持向量距离计算
- 支持向量索引，比如 ivfflat 和 hnsw

迁移里通常会先执行：

op.execute("CREATE EXTENSION IF NOT EXISTS vector")

这表示：
在当前数据库中启用 vector 扩展。


6. Python 依赖和数据库扩展不是一回事

项目里 pyproject.toml 有：

"pgvector>=0.4.2",

这表示安装 Python 侧的 pgvector 库，作用是：

- 让 SQLAlchemy 认识 Vector(1536)
- 允许代码里写 from pgvector.sqlalchemy import Vector

但这还不够。
数据库里还要启用：

CREATE EXTENSION vector

所以两层都要有：

- Python 层：pyproject.toml 里的 pgvector
- 数据库层：PostgreSQL 里的 vector extension


7. ivfflat 是建在哪里

ivfflat 不是建在 DocumentChunk 类上。
它建在：

- 表：document_chunks
- 列：embedding

更准确地说：
是在 document_chunks 表的 embedding 向量列上创建索引。


8. 为什么迁移里不用 import DocumentChunk

因为迁移里这句执行的是原生 SQL：

op.execute(
    "CREATE INDEX ix_document_chunks_embedding ON document_chunks "
    "USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100)"
)

这里的 document_chunks 是数据库表名，不是 Python 变量。
数据库只认表名，不需要 import ORM 类。

关系要分清：

- Python 类名：DocumentChunk
- 数据库表名：document_chunks


9. 关键 SQL 速记

op.execute(
    "CREATE INDEX ix_document_chunks_embedding ON document_chunks "
    "USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100)"
)

逐段理解：

- CREATE INDEX ix_document_chunks_embedding
  创建一个名为 ix_document_chunks_embedding 的索引

- ON document_chunks
  索引建在 document_chunks 表上

- USING ivfflat
  使用 ivfflat 这种向量索引类型

- (embedding vector_cosine_ops)
  对 embedding 列建索引
  按余弦距离规则工作

- WITH (lists = 100)
  ivfflat 的参数
  可以粗理解为把向量分成 100 个 lists / 簇 / 组


10. vector_cosine_ops 是什么

它表示这个向量索引按余弦距离这套规则工作。

学习阶段可以简单记成：

- cosine = 余弦相似度/余弦距离这类检索方式

面试里更稳的说法是：

- vector_cosine_ops 是 pgvector 的余弦距离操作符类


11. lists = 100 怎么理解

不是“切成 100 行”。
更接近：

- ivfflat 会把向量粗分成很多组
- lists = 100 表示使用 100 个 lists
- 查询时先找更相关的组，再在组里找最近邻

作用：

- 比全表扫描快
- 但属于近似搜索，不一定每次都是绝对最优解


12. 没有索引 / ivfflat / hnsw 的区别

没有索引：
- 每次都把 query 向量和所有 embedding 一条条比
- 最准
- 最慢

ivfflat：
- pgvector 的近似向量索引
- 先粗分组，再缩小候选范围
- 速度快很多

hnsw：
- 也是 pgvector 的近似向量索引
- 一般效果更好
- 现在很多 RAG 场景更偏向 hnsw

一句话：

- 无索引：最准但慢
- ivfflat：经典、快
- hnsw：通常更强


13. ivfflat 和 hnsw 的共同点

- 都是 pgvector 提供的向量索引
- 都服务于 embedding 相似度检索
- 都用于 RAG 检索加速

区别只是在索引实现方式不同。


14. 这个项目当前的设计

- ORM 里定义 KnowledgeBase 和 DocumentChunk
- DocumentChunk 里定义 embedding: Vector(1536)
- Alembic 迁移里建 knowledge_bases 和 document_chunks 两张表
- Alembic 迁移里再给 document_chunks.embedding 建 ivfflat 索引

所以完整关系是：

DocumentChunk 模型
-> 定义 embedding 列
-> Alembic 建 document_chunks 表
-> Alembic 在 embedding 上创建 ivfflat 索引
-> PostgreSQL 用它加速向量检索


15. 面试速记版

1) KnowledgeBase 和 DocumentChunk 是 ORM 模型。
2) ORM 只是在 Python 里描述表结构。
3) 真正落到数据库要靠 Alembic 迁移。
4) Alembic 里的 op 是数据库迁移操作入口。
5) pgvector 是 PostgreSQL 的向量扩展。
6) embedding 列定义在 document_chunks 表里，类型是 Vector(1536)。
7) ivfflat 和 hnsw 都是 pgvector 的向量索引类型。
8) 当前项目在 document_chunks.embedding 上建立 ivfflat 索引。
9) vector_cosine_ops 表示按余弦距离规则检索。
10) lists = 100 表示 ivfflat 使用 100 个 lists 来缩小搜索范围。
11) pyproject.toml 里的 pgvector 是 Python 依赖。
12) CREATE EXTENSION vector 是数据库层启用扩展。
13) ORM 负责定义，Alembic 负责执行，数据库负责真实存储。


16. 一句话总背诵

这个项目先在 ORM 里定义 KnowledgeBase 和 DocumentChunk，再通过 Alembic 把 knowledge_bases 和 document_chunks 表真正建到 PostgreSQL 里；其中 document_chunks 的 embedding 是一个 Vector(1536) 向量列，数据库通过启用 pgvector 扩展支持向量存储，并在 embedding 列上用 ivfflat 建立基于余弦距离的向量索引，用来加速 RAG 的相似度检索。
